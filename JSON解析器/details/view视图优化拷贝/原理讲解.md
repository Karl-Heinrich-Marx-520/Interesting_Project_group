# 一次性给你讲透：
1. **左值深拷贝能不能彻底避免？**
2. **怎么写才能性能拉满？**
3. **不写右值重载 `&&` 会有什么致命短板？**
4. **适配你 JSON Lexer/Parser 的最优写法**

先抛**核心真理**，杜绝误区：
> 如果你**类内部要存一份独立、独占的数据**（比如 `std::string m_input`）
> **左值永远躲不开「至少一次必要深拷贝」**
> 我们能做的是：**消灭多余拷贝、能用移动就不拷贝、不用持有就用视图零拷贝**
> 不可能在「保留独立副本」的前提下完全干掉左值拷贝。

---

# 一、先答：不写右值重载 `&&` 会怎样？
就两种写法，分别说后果：

## 情况1：只写唯一一个 `const&` 构造
```cpp
Lexer(const std::string& s) : m_input(s) {}
```
- 传**左值**（普通变量）：绑定引用 → 成员深拷贝 **1次**
- 传**右值**（临时字符串）：也被 `const&` 绑定 → 照样强制**深拷贝1次**

**后果**：
临时对象本来可以直接**移动零拷贝**，你白白浪费性能，强制做一次完整深拷贝，长字符串性能亏很多。

## 情况2：只写唯一一个 值传递构造
```cpp
Lexer(std::string s) : m_input(std::move(s)) {}
```
- 传**左值**：先拷贝一份给形参（深拷贝1）→ 再move给成员
  **多了一次完全多余的中间拷贝**，纯吃亏
- 传**右值**：直接构造形参 → move给成员，性能完美

**后果**：
日常最常用的**左值变量传参**必吃亏，平白多一次拷贝。

## 总结：不写 `&&` 重载的本质问题
**永远无法做到左值、右值两边性能都最优**，必有一边被牺牲。

---

# 二、如何避免左值多余深拷贝、提升性能？
分 **3 种层级方案**，从简单到工业级，适配你不同需求。

## 方案1：外部手动 `std::move` 把左值变右值（最简单）
不用改类的构造，调用时主动转移所有权：
```cpp
std::string big_json = "非常长的JSON字符串...";
// 把左值强行转右值，转移内存所有权，不深拷贝
Lexer lex(std::move(big_json));
```
### 原理
- `std::move` 不移动任何数据，只是**强制转成右值引用**
- 如果类是值传递+move构造：直接抢夺内存，**无深拷贝**
### 代价
- 原变量 `big_json` 变成**空的失效状态**，后面不能再用
### 适用场景
变量传给Lexer后**再也不用了**，适合JSON解析这种一次性传入。

---

## 方案2：重载双构造 `const&` + `&&`（工业标准，左右值全最优）
```cpp
// 左值进来：只做【唯一必要的1次深拷贝】，无多余
Lexer(const std::string& s) : m_input(s) {}

// 右值进来：直接移动，0深拷贝
Lexer(std::string&& s) : m_input(std::move(s)) {}
```
### 性能表现
- 左值：**仅1次必要拷贝**，无多余中间步骤
- 右值：**完全无深拷贝，只移指针**
### 关键点
即便双构造，**左值依然有一次深拷贝**——躲不掉！
因为你类里要存一份独立数据，必须复制一份，这是逻辑刚需，不是代码能优化掉的。
你能优化的只是**不要多拷贝**，不能干掉**必要的那一次**。

---

## 方案3：彻底零拷贝——用 `std::string_view`（最适合你的Lexer）
### 核心思路
Lexer **不需要拥有字符串所有权、不需要修改、只遍历读字符**
那就**根本没必要存完整 `std::string`**，改用 `std::string_view`。

`string_view` 特点：
- 只存**指针+长度**，**0内存分配、0深拷贝**
- 不管左值还是右值，全是**零开销视图**
- 只读，完全适配词法分析器只读遍历的需求

### 改造你的 Lexer（零深拷贝终极版）
```cpp
#include <string_view>

class Lexer {
private:
    std::string_view m_input;  // 改成视图，不存完整字符串
    size_t m_pos = 0;
    size_t m_line = 1;
    size_t m_column = 1;

public:
    // 一套构造兼容左值、右值、string、字面量，全零拷贝
    Lexer(std::string_view s) : m_input(s) {}
};
```
### 无敌优势
1. **彻底消灭所有深拷贝**，左值右值全都零开销
2. 只需要写**一个构造函数**，不用重载`&&`
3. 传 `std::string`、传字符串字面量、传临时对象，全都自动适配
4. 完美适配Lexer只读场景

### 唯一限制
`string_view` 依赖外部字符串生命周期，只要**外部字符串比Lexer活得久**就绝对安全，JSON解析完全满足。

---

## 方案4：存指针/引用，不存副本（不推荐初学者）
```cpp
class Lexer {
    const std::string* m_input;
public:
    Lexer(const std::string& s) : m_input(&s) {}
};
```
- 优点：**零深拷贝**
- 致命坑：容易**野指针、悬空引用**，外部字符串销毁后Lexer直接崩
初学者千万别用，大型框架才会谨慎用。

---

# 三、帮你浓缩关键结论
## 1. 不写右值 `&&` 会怎样？
- 只写`const&`：临时右值也被迫深拷贝，浪费性能
- 只写值传递：左值多一次多余拷贝，日常使用吃亏
- 一句话：**总有一方性能拉胯，做不到全能**

## 2. 左值能不能彻底避免深拷贝？
- 只要你类里**要存独立可独占的 `std::string`** → **躲不开1次必要深拷贝**
- 只能优化：**消灭多余拷贝、用移动代替拷贝**
- 若可以不存完整字符串 → 用 `string_view` **彻底零拷贝**

## 3. 给你的JSON解析器最佳选型
1. 初学简单写：用 `const&` 构造，好懂不踩坑，性能够用
2. 想性能拉满又规范：重载 `const&` + `&&` 双构造
3. **终极最优**：直接改用 `std::string_view` 做Lexer内部存储，**零拷贝、不用重载、左右值通吃**

## 4. 一句话记死
- `const&` 不拷贝，**初始化成员时才拷贝**
- 不写`&&`重载，永远有场景吃亏
- 要彻底零拷贝，别纠结引用重载，直接上 **string_view** 是最简解。
